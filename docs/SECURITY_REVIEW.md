# Security review and remediation register

Review dates: October 30–31, 2026. Baseline: `e714469d156f06dd343fe1250339783f71cf21de`. Scope: first-party application, worker, browser, storage, configuration, database migrations, CI/container files, tracked Git history, and dependency lockfile. No public deployment URL, cluster, live S3 bucket, or production host was available. Reproductions use synthetic fixtures only.

This register records all findings identified in this engineering review. It cannot guarantee that every vulnerability has been discovered. Severity assumes a restricted single-server pilot; this is not a penetration-test certificate or approval for regulated data. A source fix must also be deployed to protect a running installation.

## Data exposure inventory

- **Public by design:** repository source, README screenshots containing synthetic examples, license, authors/commit history, dependency versions, and unauthenticated health/readiness/session capability responses. API health reveals version and local execution mode, but no identity, credentials, paths or research data.
- **Private to the account:** email/name, session administration identifiers/timestamps, recovery-code count, security activity and metadata export. Stored password/session/recovery/enrollment/invitation secrets are hashes. Plaintext codes are shown only when explicitly generated and must be shared/stored privately.
- **Private to current project members:** member names/emails, uploaded filenames/content/checksums, previews, results, manifests, run errors, audit actor/actions/details and saved explanations. Viewers intentionally have research read/download access. Owners manage access; collaborators upload/run. Project owners see pending recipient emails. Grant membership only to intended recipients.
- **Operator secrets/data:** `.env`, PostgreSQL connection/passwords, optional AWS/AI/metrics secrets, `.data` or custom DATA_DIR, persistent volumes, backups and logs. Ignore rules and Vite denies reduce accidental publication; host/backup access controls remain necessary. Do not place any secret in a `VITE_` variable, `public/`, tracked file, screenshot, URL or GitHub Pages bundle.
- **Optional external transfer:** explicitly enabled AI would receive the question, result/parameters, artifact names/checksums and run ID. It does not receive raw upload bytes and cannot execute actions. External AI is disabled by default and in tracked Compose. A deliberate future enablement needs privacy, cost and prompt-injection review; generated explanations remain untrusted text.
- **Residual copies:** authorized users can save downloads, screenshots and clipboard/recovery exports; browsers/OS/backup systems can retain copies. No web app can retract those copies. Never upload regulated/restricted data before institutional approval.

## Verification and limits

Startup remediation also addresses the reported “Request failed” screen: the development frontend waits for API readiness, uses the configured API port, and accepts loopback aliases only in development. Initial session requests retry transient startup failures; offline/static-host errors now explain the missing service. A local browser verification reached the existing dashboard successfully. No GitHub Pages site or repository deployment was returned by the GitHub API.

- Existing and adversarial automated suites cover identity/session recovery, project isolation and roles, invitation lifecycle, CSRF/origin, encoded routes, file checksums/size/traversal, malformed CSV, quota/idempotency/cancellation/recovery, private Vite paths, log redaction, and browser session epochs.
- Local Windows tests skip symlink creation when the OS denies that privilege; Linux CI must execute that case. PostgreSQL-backed CI supplements embedded PostgreSQL tests. Container build/scan and CodeQL run on GitHub Linux runners; see the actual checks for this branch/PR.
- `npm audit --audit-level=moderate` initially returned zero known advisories. A later advisory refresh found three moderate dependency-chain entries, resolved by the patched override above. The redacted current/index/history scanner initially examined 196 historical text blobs with no matches; final counts change as commits are added. GitHub secret-scanning API returned no open alerts. None of these checks proves absence of secrets or unknown dependency flaws.
- Static first-party review checked SQL parameterization, UUID validation, resource membership, React text rendering, cookie/CSRF/CSP headers, workflow allowlisting, input integrity and configuration boundaries. No raw user SQL, arbitrary command execution, unsafe HTML renderer, browser credential persistence or executable user workflow was found. This does not replace independent dynamic testing of a deployed service.

## Required operator actions before public research use

1. Revoke the previously removed local provider key; review any historical logs, forks, releases, screenshots and existing deployments for exposure. If a development server was publicly reachable, treat its database and research files as potentially disclosed, rotate sessions/credentials and assess notification obligations privately.
2. Review migration/backup instructions before upgrading existing deployments. Verify email identity out of band, approve legitimate old accounts, issue individual enrollment codes, and regenerate recovery codes after a password change/reset.
3. Configure agreed `main` protection/required checks/reviewers. Restrict repository admin and deployment credentials. Keep code-scanning and dependency/security alerts reviewed; automation creates PRs rather than silently deploying updates.
4. Deploy the fixed revision with HTTPS, host validation, reverse-proxy body/time/rate limits, private DB/network/storage, least privilege, disk monitoring, restrictive host ACLs and an explicit single-replica limit. App rate limits are process-local/IP-based; distributed/account-aware limits and load evidence are required before scaling/public onboarding.
5. Configure encrypted, access-controlled, versioned/off-host backups with retention and execute a restore drill. Research/audit retention and deletion need a documented policy; archiving is reversible and is not deletion.
6. Decide accepted file types and malware handling with the institution. The app treats uploads as opaque data/attachments and only parses bounded CSV; it does not provide antivirus scanning or guarantee that downloaded files are harmless.
7. Validate live S3 IAM/TLS/integrity, deployed headers/cookies, provider settings, independent penetration testing and real load/capacity. GitHub Pages alone cannot host the authenticated Node/PostgreSQL backend. No deployed URL or hosting access was provided here.
8. Before institutional/regulated use, establish verified identity/MFA/SSO, privacy/retention obligations, incident response ownership, monitoring/alert delivery, an HPC allocation and scheduler authorization, and domain-specific scientific validation.
