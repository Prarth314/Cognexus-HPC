## Measured performance

The unmodified machine-readable result is [benchmark-2026-11-01.json](evidence/benchmark-2026-11-01.json). It records source revision **`48984a03a1ef956d25c0305d78f2b844207811c8`**; documentation edits were pending (`workingTreeDirty: true`). The subsequent `e2e5c3b` change guards cleanup after failed/ambiguous commits; no benchmark of that failure path or before/after speedup is claimed.

One compiled Node API/worker process; persistent PGlite and private disk; localhost HTTP; AMD Ryzen 7 8840HS, 16 logical CPUs, approximately 15.3 GiB system memory. This was a shared developer workstation, not an isolated performance laboratory. One project, **10,000 synthetic CSV rows / 147,902 bytes**, 13 uploaded versions including warm-up. Three warm-ups excluded; request measurements include response body handling/validation. Preview validation covers the bounded preview, not the entire CSV; the statistics workload validates/processes the complete dataset.

Nearest-rank quantiles; with 10 samples, p95 is the maximum. Only the file-list experiment uses concurrency three; all job tests are sequential. Its 30-request short burst measured **425.18 requests/second** over the measured burst interval. **This is not sustainable throughput**: the default API allowance remains 120 requests/IP/minute, and the benchmark waits 61 seconds between job and read phases to preserve it. No public/shared deployment was load-tested. The end-of-run server RSS sample was **304,046,080 bytes (~290 MiB)**, including embedded DB/worker process overhead; it is not peak memory or evidence that 128 MiB bounds the whole application.

Queue wait dominated the small reference job, consistent with the existing one-second polling interval. No index or scheduler optimization was made on this sample: the project was tiny, request latencies were small, and no representative production bottleneck was established. There is no before/after improvement claim. Large multi-project PostgreSQL performance, network/TLS behavior, long-running workloads, resource peaks, and hosted SLOs remain unmeasured.

## Key decisions and ownership

| Decision                                                                        | Reason / tradeoff                                                                                                                                  |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Retain Fastify, PostgreSQL row locks, and one local worker                      | Complete existing workflows without adding a second queue or unneeded distributed infrastructure; global multi-replica controls remain future work |
| Fence completion by status and attempt; check retention after ambiguous commits | Prevent cancellation/stale-attempt overwrite and avoid deleting a successful committed artifact after an acknowledgment failure                    |
| Register result, artifact metadata, and audit event atomically                  | DB correctness is verifiable; external object bytes still require best-effort cleanup and read-only reconciliation                                 |
| Bounded approved computations only                                              | Reproducible local CPU reference workloads; no arbitrary-code sandbox, Slurm, or institutional compute claim                                       |
| Offline paired backups and disposable restore targets                           | Explicit small-pilot consistency model, supported official PostgreSQL tools, no production overwrite or automated data deletion                    |
| Measure before optimizing                                                       | Separate queue wait from worker time, publication, HTTP latency and short burst throughput; avoid unsupported scale claims                         |
